# 调查的工作循环

以可以回答的安全问题组织工作。黑板保存事实、解释和进度；下面的编排由本场景负责，不进入通用内核、投影或 lint。

## 1. 先获得能选择切入点的模型

读取版本与相关本地变化、启动／注册代码、关键接口、权限与数据模型，画出最小的“谁通过什么入口操作什么资源”。部署、框架、依赖和产物没有依据就标未知，不从项目名称猜。

按实际目标挑切入点：

- 一份危险输入进入解释器：追数据、类型、变换和最后使用，读 [技术专项](techniques.md)。
- 一个资源有多种操作：枚举角色与 read/write/delete/export/bulk 的保护差异，找预期保证失效的路径。
- 一个多步动作：比较每一步前后状态、失败与回滚、并发及重复请求，不假设必须存在危险函数。
- 一个补丁或异常：从变更前后的保证、已知实例或观察开始，用 [调查方法](investigation.md) 建立候选解释。

从最高后果且低信任可达的边界开始，但不能用风险排序替代事实核查。新发现的调用方、失败路径或共享组件可以改变下一项调查；不坚持初始分类。

## 2. 把范围切成问题，不只是文件

一个有效事项例如：

> 普通成员对同一文档的 list、download、export、delete 是否都按其集合权限判断？注册层、服务层和查询层哪一层提供保证？

这比“看 api/ 全部文件”更容易分配、证伪和恢复。给每个事项保留：

| 字段 | 内容 |
| --- | --- |
| 目标与身份 | 当前源码／产物版本、低信任主体、资源与操作 |
| 基线保证 | 产品／调用契约要求，以及实际提供控制的代码位置 |
| 切入点 | 已知入口、关键调用者／被调函数、相关配置或历史补丁 |
| 当前解释 | 已知事实、具体候选与最有力的竞争解释 |
| 判别方式 | 哪个读取或最小检查可以改变判断，何种结果分别支持谁 |
| 覆盖边界 | 实际查过的分支、方法和未查范围；不以无发现代表已查 |

简单事项放目标或候选 detail；有独立进展、复用或负责人时再建 question／coverage。不要生成无意义的全维度笛卡尔积。

## 3. 调查、记录、修正

用 [调查方法](investigation.md) 核对真实保证和竞争解释。每次关键转折保留足以继续的摘要：新的代码事实、实验到达性、支持／反证、仍未知的条件、下一项有区分力的动作。

发现不属于当前问题的新入口或缺陷机制时，把位置和为什么值得查单独回传；有独立工作才另开事项，不让原调查无限扩张。需要未知依赖、缺失产物、工具模型或部署事实时，先写清具体缺口与需要看到的结果。它是可以恢复的待办问题，不是让底座自动调度的状态机。

长日志和整段逐函数解释留在私有证据位置，黑板保留关键保证与来源；没有结论变化时无需逐命令记账。研究中间文件未经导入不算已保存到黑板。

## 4. 并行回传与独立验证

多个事项实际独立时再并行，任务包含上表信息和 [回传模板](../assets/investigation-brief.md)。默认协调者写共享黑板；子任务写自己的私有回传，不能因有 agent 身份就越过宿主的写隔离。

回传必须区分“检查结束”“环境失败”“未到达目标”和安全结论。格式合法只证明可消费，协调者还要核对：

1. 位置与版本是否真实，事实与推断是否分开，关键调用者和最强控制有没有被忽略。
2. 输入、身份、权限、状态、配置是否兼容；影响是否超出证据，是否将 PoC 草图写成执行结果。
3. 是否真的回答了事项，未解决的分支是否公开；一个事项的结论不能替代相邻事项覆盖。

正式保留的确认问题与具体待验证候选应交给未提出它的审阅者。验证者重建主张并尝试推翻：确认控制是否有效、攻击者是否有该能力、结果是否真正越界。给它必要上下文与证据，不灌入其他验证者的结论。可一次审一组独立条目；不固定三轮或每条多个 agent。只有单人能力时做独立于原假说的反证检查，明确没有独立审阅者。

如果复核改变根因、入口、边界、关键条件或影响，需要重查这些部分；不能仅替换文字后沿用原验证。不同审阅者的分歧保留为带范围的判断，不投票决定真假。

## 5. 每轮综合要产生实际后果

检查本轮结果是否带来：

- **共享条件**：同一配置、框架语义或部署事实影响多项结论。核对一次该事实，再逐项检查其他前提，不自动升级全部候选。
- **同源机制**：同一错误保证影响多个操作。先保留实例差异，再用已知实例校准模式、搜索变体。
- **可组合路径**：A 的具体输出能否满足 B 的前提？核对主体、数据、权限、版本、状态和时序。共享分类不构成链，必要条件与替代路线分开。
- **覆盖缺口**：被漏掉的注册入口、错误路径、存储模式或生命周期需要新事项。扫描无命中时先核对工具是否能看到它。
- **错误解释**：什么证据撤回了候选？哪个实验只是没有到达？哪些无效模式应避免再追？

如果没有新增关联，记录即可；不要为了证明做过综合强行建根因。用“这项事实改变了哪一判断／下一次检查”检验综合价值，不以边数或发现数量衡量。

## 6. 版本变化与交付

继续旧任务前核对相关代码、产物身份、调用方和条件变化。相同提交号不保证本地文件相同，相同目录名不保证反编译内容相同。历史记录只在相关源与条件重新核对后用于当前范围。

修复后，旧版本成立的漏洞仍是旧版本事实。新版本用新的证据描述原路径及同源路径是否受保护，区分源码判断和真实运行结果。执行与负对照见 [验证与执行](execution.md)。

报告从裁定生成，列范围／版本、成立问题、重要反驳、具体未知、覆盖与缺口、修复及实际验证方法。归并保留实际节点／源码路径，去重不按文件名、标题或 CWE；同根因但不同控制、影响或修复可能仍须分开。记录形式见 [记录与裁定](records.md)。

结束条件是所述范围的判断有可复核证据，仍在调查、外部阻断和未审范围被明确交付，报告与黑板一致。工具失败、范围有限或零确认问题不允许被包装为全库安全，也不要求继续凑发现。

依据：[Cloudflare 的独立验证、持久化和增量覆盖](https://blog.cloudflare.com/build-your-own-vulnerability-harness)、[Trail of Bits 的上下文与变体分析](https://github.com/trailofbits/skills)、[Doyensec 的误报排查经验](https://blog.doyensec.com/2026/02/03/outline-audit-q32025.html)。这些方法由 Agent 使用现有黑板完成，不要求企业 harness、额外数据库或专用 Hook。
