# 记录与裁定

这些是本审计场景的约定，不是黑板内核的 schema 或状态机。只记录有助于未来判断的内容；不要让记账成本吞掉源码研究。

## 身份、版本与标签

每次审计使用稳定 `audit=<run-id>` 标签，目标 detail 写实际源码位置、版本与范围。需要跨单元过滤时，选用 `component=<name>`、`class=<name>`、`unit=<key>`、`fingerprint=<key>`。值须来自实际目标；没有用途就不添标签。

用 `key=value` 是因为现有 `--group-by tag:key` 识别这种格式；`component:web` 只是普通字符串，不会自动进入该分组。不要把 ID 前缀当类型或把 fingerprint 当黑板节点 ID。

fingerprint 表示一个逻辑候选身份：稳定的控制失效机制、边界与受影响操作组合。不要只用行号、漏洞类别或文件名生成；发现新根因／边界时建立新候选。跨版本共享 fingerprint 时，以源码版本区分各份证据和裁定。

## 最小记录粒度

| 记录 | 建议表达 | 何时独立成节点 |
| --- | --- | --- |
| 范围与系统模型 | `goal` 的 detail | 本次实际审计目标 |
| 候选 | `finding`，先 `status=open`、`confidence=suspected` | 已有具体边界问题，尚待核查 |
| 证据 | `fact`／`observation`／`result` | 可复核事实、实验结果或重要反证 |
| 共享前提 | 自定义 `condition`，明确真假／未知及适用范围 | 被多个候选依赖，或决定关键结论 |
| 根因机制 | `fact` 加 `role=root-cause` 标签 | 机制已证实，值得供多处引用 |
| 覆盖单元 | 自定义 `coverage` | 有独立范围、结果或负责人 |
| 开放问题 | `question`／`hypothesis` | 有可独立回答的未知事项 |

单个候选的证据可先放在 detail 中；复用、争议或需要追踪演变时再拆。没有足够证据，不把“预期要求”写成“控制已经存在”的事实。候选升级时编辑原记录，避免复制出另一条“已确认 finding”。

复杂事项使用[调查回传模板](../assets/investigation-brief.md)：在当前问题的 detail 保留已知事实、真正竞争的解释、已做判别检查与实际结果、仍缺的事实及下一项能改变判断的检查。局部 H1/H2 不是黑板 ID；假说之间不因竞争自动互为反证。可复用、独立演变或有争议时再拆成 hypothesis／question／证据节点，不能把每个模板字段都变成节点。

模式、查询和工具模型只在影响解释或覆盖边界时保留：精确种子命中什么、放宽了哪一条件、新命中与排除对照、未建模的 source/sink／摘要／入口。语法正确、空结果或大段代码摘要不能替代这些事实。

## 候选 detail 的内容

以下是字段提示，不要求固定 Markdown 标题或创建另一套 JSON 台账。直接由 hunter 回传或写入节点 detail：

```text
源码：仓库／版本／相关本地变更；实际文件与正整数行号。
范围与单元：本候选回答哪个边界问题。
主体与输入：最低所需权限；可控值、动作、时序或对象。
预期控制：控制的依据；保护的主体或资源。
实际路径：入口、关键调用／变换／检查、敏感操作或状态变化。
安全结果：具体谁能对谁的什么资源做什么，证据支持到什么程度。
条件：逐项写已证实／被否定／未知，标明版本与配置范围。
支持与反证：实际源码位置、已有节点 ID、可信证据文件及解释。
证伪事项：当前解释与最有力的竞争解释；何种事实能区分它们；已做检查的预测、观察与到达性；下一项会改变判断的检查。
裁定：candidate／confirmed／needs_validation／rejected；理由与适用范围。
验证方法：source／local；真实执行才填写输入、命令、限制与观察。
修复：在最后可信决策点应满足的要求、最小改动与行为回归建议。
```

有些字段暂时未知就写未知，不补造入口、复现结果或修复细节。对未经验证的机制使用“疑似／待核查”，不要用标题把假设写成事实。

## 三个维度与报告裁定

内核接受的常用取值：status 为 `open`、`active`、`done`、`blocked`、`dead`、`confirmed`、`refuted`、`deferred`、`superseded`；confidence 为 `suspected`、`static-confirmed`、`reproduced`、`confirmed`；severity 为 `critical`、`high`、`medium`、`low`、`info`。类型和关系可自定义，这三个枚举不能随意新增。

| 审计含义 | 节点记录方式 | 交付 |
| --- | --- | --- |
| 候选仍在检查 | `open`／`active`；`suspected`；不提前填严重度 | candidate，不计确认问题 |
| 源码已核对，关键条件仍未知 | `blocked`；可为 `static-confirmed`；detail 写精确阻断 | 满足具体边界候选门槛时为 `needs_validation`，不带严重度 |
| 所述范围内边界与结果已证实 | `confirmed`；按实际证据为 `static-confirmed` 或 `reproduced` | confirmed，严重度仅覆盖证实的影响 |
| 证据推翻候选 | `refuted`，关联反证；不删除历史 | rejected，说明反驳范围 |
| 新解释确实取代旧解释 | 新论断 `supersedes` 旧论断；旧节点显式 `superseded` | 保留旧解释与版本历史 |

这是 Agent 主动作出的裁定，不是字段间的自动转换。`static-confirmed` 不隐含真实复现，`reproduced` 不证明线上配置或互联网暴露，证实一个事实也不会自动确认它支持的漏洞。

源码可以充分证明一个条件化缺陷；如果条件是已知、受支持且明确限定的配置，不必为了确认“某部署目前是否使用它”一概降为未知。反之，声称“当前默认服务低权可达”时，缺少真实挂载／继承授权依据就不能确认该主张。写清究竟评估产品行为、某配置，还是某个实际部署。

对已带 severity 的旧记录进行撤回或降级时，公开 CLI 不保证能清空该字段；保留历史评分并在裁定中明确已失效／不适用。派生报告依据当前裁定筛选，不能因字段仍有 high 就继续输出为确认问题，也不要直接修改事件文件清空它。

## 关系语义

全部读作 `from relation to`：

| 含义 | 方向 | 不能据此推出 |
| --- | --- | --- |
| 事实支持结论 | 证据 `supports` 候选／条件／根因 | 单条支持已证明全部结论 |
| 事实反驳结论 | 反证 `contradicts` 候选／条件 | 已自动更新 status |
| 实例由已知机制导致 | finding `caused-by` 根因机制 | 同类别／同目录即同根因 |
| 成立需要某项前提 | finding／链论断 `depends-on` condition | 前提已真，或所有前提已满足 |
| 实例违反某项要求 | finding `violates` 要求论断 | 要求本身是导致漏洞的根因 |
| 检查产生了发现 | coverage `yielded` finding | coverage 已完整或安全 |
| 论断取代旧解释 | 新论断 `supersedes` 旧论断 | 旧解释必然为假 |
| 确知归属，暂无更强含义 | 节点 `related-to` goal／相关节点 | 因果、证据或利用依赖 |

`derived-from` 可替代反向 `supports`，同一事实无需两边重复记录。执行任务受未知事实阻断，可把问题节点设为 `blocked`；不要把“需要前提成立”混写成“该前提在阻挡漏洞”。

关系不附带求解器。本场景复用已有 `depends-on` 表达必要依赖，多个此类前提均须满足；若有替代路径，分别记录路径及其条件并在 detail 说明，不能只看图上存在一条路就声称可利用。条件核实后，Agent 逐项核查其关联结论，显式更新相关裁定。

## 反证、失败实验与修复历史

失败实验可以是已确认的 `result`，支持的只是“此输入在此环境观察到某结果”。明确区分环境未就绪、未到达目标、有效负结果与有效正结果；具体判断见[验证与执行](execution.md)。没有命中不是普遍安全证明，读取历史日志不能冒充本轮亲自执行。环境失败可支持某项运行阻断，但不能因此连 `contradicts` 到漏洞候选。

反证充分时，先记录事实及 `contradicts`，再显式改候选为 `refuted`。替代解释使用 `supersedes`；不要为了让图清爽删除反例或失败候选。

修复验证记录新版本、原问题路径、同源路径及行为结果。旧漏洞只要在旧版本成立，就不因新版本修复被改写为假。旧 `reproduced` 也不自动覆盖新版本的实验。

## 报告映射

报告条目与图节点是不同粒度。保留一个有理由的显式映射，例如：

```text
report_id: R-01
node_ids: [实际 finding ID A, 实际 finding ID B]
reason: 两个入口使用同一个错误租户选择函数；影响和修复一致。
source_ref: 实际审计版本
```

可把映射写到已有目标／归并判断的 detail，条目多时使用带 `role=report-map` 的普通节点。报告与映射文件从这些记录派生；报告修订若改变结论，先更新黑板裁定和证据，再重生交付。

共享根因不自动归并：不同权限起点、资源边界、影响或修复位置可能需要不同条目。合并时完整列出实例与影响，允许多个节点映射同一条目；证据／条件也可被多个条目引用。fingerprint 支持候选身份与去重，不能替代归并关系。

导出前显式筛选本次审计与当前裁定。内核 Markdown 导出忠实呈现记录，不会替审计者裁定；SARIF 不会依据 status/confidence 自动排除反驳项，其指纹基于节点 ID，也不是这里的逻辑 fingerprint。
