# 从疑点推进到可区分的证据

本页用于选择下一处源码或最小实验，不要求逐函数审完整库。先用一句话写出“当前哪两种解释都符合已知事实”，再选能让它们产生不同观察的动作。仅当动作改变候选、条件、覆盖或下一步时，按 [记录与裁定](records.md) 留在黑板。

以下黑板片段均为合成示意，ID、函数与位置不代表实际发现；实际记录须补齐源版本和精确位置。关系沿用公开 CLI 的 `supports`、`contradicts`、`depends-on`，不隐含自动裁定。证据来源／成熟度与漏洞裁定分开：源码读清不等于运行复现，运行结果也不自动证明安全影响。需要执行时先读 [执行与证据](execution.md)，本页不授权运行、安装或构建。

## 1. 选择性函数契约：找出谁真正建立了保证

**何时选用：** 调用方把某个返回值当成授权、存活、长度或状态保证，但该保证究竟由谁建立还不清楚。[1]

1. 先读该调用点与被调实现，围绕一个具体保证分析；不要从整个目录逐函数铺开。
2. 列出显式输入及可控范围，再找隐式输入：全局表、当前身份、配置、时钟、线程局部值、锁、缓存和事务快照。
3. 写清前置条件及其建立者；再按分支写本函数实际建立什么、返回什么、修改什么、把什么对象或回调交给外部。名字、注释和接口承诺与实现证据分开。
4. 对消费此保证的调用方，核对它是否检查错误码、是否初始化输出参数、是否遵守所有权／锁约定。若有分派、FFI、插件或虚调用，定位实际实现；不可见实现留作未知。
5. 沿“保证可能断裂”的位置扩读：改变同一状态的写入者、释放者、取消路径、回调和失败清理。只递归追踪影响当前保证的依赖。

可用一条短契约组织读取，不必为每个函数建立文件：

| 要素 | 必须落到的具体问题 |
| --- | --- |
| 输入／隐式状态 | 哪个主体控制 ID、长度、对象、调度或当前状态？ |
| 前置条件 | 要求已持锁、对象存活、长度合法；哪条路径建立它？ |
| 建立的保证 | `return true` 是否在每个成功分支都意味着同一件事？ |
| 调用关系 | 调用方依赖什么，被调方真的保证什么？ |
| 错误与副作用 | 失败是否留下已写状态、旧输出指针、未释放引用或已发消息？ |

**身份不等于存活：** 假设 `find_handle(id)` 只验证表项 ID 相等，调用方却据其非空结果使用资源。下一读应是表项关闭／回收路径，而非继续解释非空判断。若关闭先设 `closing`、后移出表，则“命中身份”没有证明“仍可使用”；但仍不能直接称为 UAF，还须查资源何时释放、引用何时取得、锁是否跨查找与使用持续有效。即使原子增加引用计数，也不能自动证明它发生在最后一次释放之前。

**退出／未知：** 当前保证在相关路径由明确代码建立，可结束此局部契约；发现缺口则形成可证伪候选。若回收者、实际绑定或调用约定不可见，精确记录未知，不把“未找到建立者”写成“全系统没有控制”。

黑板携带示例：

```text
F-contract：find_handle 仅建立 ID 匹配，不检查 closing（源码事实）。
F-contract supports H-live：关闭窗口可能取得不可用句柄（候选）。
H-live depends-on C-reclaim：引用取得前是否可能回收？未知。
下一读：close_handle 的移表、释放与锁边界；原因：决定身份缺口是否产生生命周期后果。
```

## 2. 竞争解释：设计最小区分性检查

**何时选用：** 某个输入没有触发、断言失败、扫描无命中，或多个根因都能解释同一现象。[2]

1. 写出两种竞争解释及各自预测。例如 H1：“特殊值到达索引运算，范围保证失效”；H2：“注册／解析层已拒绝该值”。另把“样本没到此路径”作为需要排除的解释。
2. 先选无需运行的区分点：注册表是否包含该功能，解析器会生成什么值，边界谓词支配哪些分支，构建配置是否包含此实现。读到这些位置能排除哪些解释，要事先说清。
3. 静态事实仍不足且允许执行时，选最靠近分歧点的观察：目标入口是否抵达、运算前实际值、状态转换顺序、失败返回码。设置一个已知合法的对照样本；每次只改变一个决定性条件。
4. 比较预测与观察，而不是把“没崩溃”当答案；若观测点过早、输出含混或优化使变量不可见，改读源码或选更直接的观察，不重复同一无信息实验。

| 实际观察 | 能支持什么 | 下一步 |
| --- | --- | --- |
| 缺依赖／构建失败／模块不存在 | 当前环境不能完成此检查 | 查现有构建描述、注册与可用入口；不现场安装补齐 |
| 输入被前层拒绝，目标分支未抵达 | 此样本未检验目标命题 | 定位拒绝谓词，调整单一条件或收窄入口主张 |
| 已抵达目标，受测条件下未出现预测结果 | 此版本、输入、配置／调度下的负结果 | 比较真实值、控制与预测，决定反驳该实例还是改解释 |
| 断言／检测器命中 | 此构建下某不变量被破坏 | 核对构建模式、实际操作与影响，不直接升级为利用结论 |

Big Sleep 的可迁移教训是：原样本依赖缺失模块，失败没有检验目标逻辑；研究者转查可用入口，才推进到真实路径。其后还须区分 debug 断言与 release 的运算行为。既有模糊测试未发现问题，也可能因为扩展未启用或 harness 使用不同版本；不能据此推断路径安全，也不能据单个案例推断一种方法普遍优于另一种方法。不需要复制文中的触发语句或利用步骤。

**退出／未知：** 一项观察明确区分两解释时，更新解释并选择下一分歧点；若路径到达、配置或调度无法确认，保留未知及最小缺失观察。环境失败、未抵达和负结果分别记录。

黑板携带示例：

```text
R-probe：模块未注册，入口断点未抵达；这是环境阻断，不反驳 H-index。
H-index depends-on C-entry：受支持配置是否能抵达该运算？未知。
下一读：模块注册与发行配置；原因：先确认可达性，避免重复无效样本。
```

## 3. 双向证伪：既质疑漏洞，也质疑想象中的防御

**何时选用：** 危险操作附近存在检查，或有人以“内部值”“已经校验”“单线程”排除候选。[1]

1. 从操作反向列出真实控制谓词，再正向检查每条相关入口是否必经它们；错误返回、条件编译、短路分支、异常和回调都可能改变控制范围。
2. 把漏洞所需条件与路径谓词并列求交，而不是凭代码外观判断。例如 `n >= header` 仅在比较与减法的类型／值一致时证明减法不下溢；还要核对随后缩窄转换、乘法、偏移和实际分配容量。
3. 同时核对下界与上界、字节与元素单位、哨兵与普通索引。检查的是 `header_len` 却使用 `body_len`，或按旧容量检查再写重分配后的对象，都不能直接沿用保证。
4. 对每个“已有防御”问：检查哪个对象与版本？使用是否经过别名、重入或异步挂起？锁、引用、不可变副本或事务是否覆盖到使用结束？为竞态列出写入者与可行交错；为排除竞态列出实际同步关系。
5. 再尝试推翻攻击者能力与安全后果：谁写入输入，能控制哪部分，哪位主体的资源受损？内部存储只在写入者、导入、迁移、插件、权限和历史数据来源均符合信任假设时才可当作可信；“来自数据库”本身不是保证。

**收窄上游启发式：** `assert` 只有在所评估构建中保留、条件有效且失败语义适当时才可能拦截操作；断言引发的可达共享服务中止也需单独评估。单线程不自动排除信号、重入回调或异步时序问题。主控制存在只能反驳它实际覆盖的路径；不能凭控制名称推断所有入口安全。

**退出／未知：** 若路径谓词与违规条件无交集，或真实控制阻止同一对象上的同一操作，反驳这一具体候选。若找到可满足的违规条件，继续核对边界后果。防御或攻击前提缺证据时保留未知；不采用上游“任一 gate 未过就判 false”的二值规则，也不将安全影响限定为 RCE／提权／泄露三类。

黑板携带示例：

```text
F-bound：入口 A 在同一不可变 n 上保证 n>=16，随后仅执行 n-8。
F-bound contradicts H-underflow-A；显式将该实例裁定为 rejected。
H-underflow-B 仍开放：入口 B 用的是别名长度；下一读其写入者，不把 A 的反证推广给 B。
```

## 4. 变体分析：先校准种子，再一次放宽一个轴

**何时选用：** 已有源码支持的缺陷机制或明确待检模式，需要寻找同机制的其他实例；没有种子时先做契约／边界分析。[3][4]

1. 把种子写成“输入／状态条件 + 缺失保证 + 受影响操作”，并保存一个足够精确、能命中已知位置的搜索。若搜索零命中，先查版本、路径、语法和提取／模型，不直接断言机制理解错误。
2. 第一轮只放宽一个轴：标识符、包装调用、类型边界、状态迁移或目录范围，择一。阅读新增命中的控制与调用方，再决定下一轴；不要同时替换函数名、信任来源和操作类别。
3. 保留真正相似但安全的反例：例如同样使用特殊索引的调用点有有效下界检查。搜索应尽量覆盖缺陷实例，并能解释反例为何不同；不为消除噪声把种子独有命名重新加回来。
4. 对原生库可从“特殊状态值被当普通数值”扩至其他转换／分配使用；对并发可从一个无锁读取扩至同一状态的其他读取者、释放者与回调。逐项确认机制，不能只凭相似语法认定同源。
5. 若已有静态查询能力，先列出它识别的入口、操作和函数摘要，与手工读到的边界比对。缺少包装库、FFI、回调、函数指针或别名模型时，查询无命中只表示当前模型没有找到；按真实 API 契约补模型，不把猜测摘要当代码事实。
6. 写清搜索范围及遗漏：未提取的构建单元、平台分支、生成代码、未知动态分派。文本搜索可补名称遗漏，不能证明生命周期、别名或 happens-before；不要把状态问题强行简化成污点传播。

**退出／未知：** 已选扩展轴的新增命中均已解释，可结束该轮并声明范围。噪声上升时收紧或改工具，并保留未处理命中；不采用固定“噪声超过一半即停止”的完成门槛。模型缺口与待确认实例保持开放，无命中不等于全库无变体。

黑板携带示例：

```text
V-round：精确种子命中；本轮只扩包装调用，新增 A/B；A 有下界检查，B 待查。
F-A-guard contradicts H-A；H-B depends-on C-wrapper-contract（未知）。
覆盖缺口：插件分派未建模；下一读 B 的包装实现，因为它决定负值能否传入。
```

## 5. 差异审查：比较不变量，不止看增删行

**何时选用：** 评估提交、修复或重构是否改变边界保证；先明确基线与目标版本，保留本地改动信息。[5]

1. 从旧版受影响路径提取一个有依据的不变量，如“发布句柄前取得存活引用”“提交后只通知一次”。同时读取旧调用方与实现，区分意图、旧版实际保证与已知旧缺陷；不假定旧版安全。
2. 阅读新版完整函数与关键依赖，把差异翻译为行为：哪些输入／状态现在可通过，检查提前还是延后，返回值／所有权／错误语义变成什么。纯移动也可能改变临界区或异常覆盖。
3. 遇到删除检查，查其引入提交、修复背景、相关测试与后续演变；查新版是否把控制移到共享层，且旧调用方是否真的必经该层。提交说明只解释意图，不能证明实现满足意图。
4. 追踪所有受该契约变化影响的调用类别：直接调用、包装、回调和 FFI。读它们如何消费结果，尤其是旧错误码、新的部分成功、输出参数、释放责任及取消路径。
5. 对状态与并发，比较检查、写状态、外部副作用、解锁及通知的顺序；原子性或失败回滚改变可能让未修改的调用方暴露新窗口。把旧／新路径各画成短事件序列，找第一个保证不同的位置。
6. 若需要验证，优先选择在旧／新版预测不同的同一条件与样本，并遵循 [执行与证据](execution.md)。已有测试只说明覆盖其断言与构建条件，测试缺失或调用者数量不能直接给出漏洞等级。

**退出／未知：** 能逐项说明相关不变量是保持、迁移、削弱还是无法判断，并给出对应调用路径，即可结束所述差异单元。历史不可达、宏配置或外部调用约定缺失时说明具体阻断；不要仅凭删除安全提交中的代码确认回归，也不强制切换工作区或先理解全库。

黑板携带示例：

```text
D-order：旧版 lock→check→retain→unlock；新版 lock→check→unlock→retain。
D-order supports H-window；H-window depends-on C-close-writer（回收是否可在窗口内发生，未知）。
下一读：未修改的 close 调用链与最终释放；原因：顺序变化只有与可行写入者结合才能定性。
```

## 一手依据与采用边界

- [1] [Trail of Bits Skills](https://github.com/trailofbits/skills)：参考 `audit-context-building/.../resources/ANALYSIS_FORMAT.md`、`FUNCTION_MICRO_ANALYSIS_EXAMPLE.md` 以及 `fp-check/.../references/false-positive-patterns.md`、`gate-reviews.md`。采用前置／建立保证、跨函数读取和谓词反证；收窄为按疑点选读，不照搬逐函数铺开、全量清单或二值 gate。
- [2] [Project Zero：From Naptime to Big Sleep](https://projectzero.google/2024/10/from-naptime-to-big-sleep.html)：采用环境诊断、路径到达、构建差异与 harness 覆盖反思；不复制触发／利用材料，不把实验性结果泛化为能力保证。
- [3] [Trail of Bits：Variant Analysis](https://github.com/trailofbits/skills/blob/main/plugins/variant-analysis/skills/variant-analysis/SKILL.md)：采用精确种子与单轴扩展；去掉固定噪声阈值、命中即评级和必须产出 CI 规则的要求。
- [4] [Testing Handbook：CodeQL Advanced usage](https://appsec.guide/docs/static-analysis/codeql/advanced/)：采用先核对 sources／sinks／summaries 再补库模型；不引入安装、建库命令，也不以数据流模型代替状态／所有权推理。
- [5] [Trail of Bits：Differential Review Methodology](https://github.com/trailofbits/skills/blob/main/plugins/differential-review/skills/differential-review/methodology.md)：采用基线不变量、删除控制历史、调用方与副作用审查；不按文件数、代码年龄或调用点数量机械定级。
