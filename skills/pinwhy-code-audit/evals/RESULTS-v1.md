# 本轮验证记录

这是本包的合成验证记录，不是对真实项目的漏洞审计。六个受评任务使用相同的已配置通用 task 模型与工具权限，各自独立上下文、板根和输出；每场景每组运行一次。场景组显式读取本包，基线组只读取通用 pinwhy Skill。判分由协调者依据实际报告、公开 CLI 读回的节点／关系和检查点完成，未做盲评或重复采样。

## 行为结果

每场景有五项断言，详见 [用例](evals.json)。节点拆分方式不同但语义等价时不扣分：一个候选内保留两个实例路径，和两个实例节点归并，都能正确表达问题。

| 场景 | 场景 Skill | 通用 Skill 基线 | 实际观察 |
| --- | --- | --- | --- |
| 真实租户越权、同源实例与安全对照 | 5/5 | 5/5 | 两组都识别发票／附件越权并归并一条报告；都保留正确租户绑定与固定 printf 参数数组的排除理由；记录为静态核对 |
| 外部宿主入口与授权未知 | 5/5 | 5/5 | 两组都没有确认默认 HTTP 低权 RCE，没有给未决主张严重度，并要求补齐宿主调用、挂载、输入与授权证据 |
| 中断恢复与源码修复 | 5/5 | 5/5 | 两组都从黑板恢复旧实例、反驳项和未知；核对 fixture-v2 的 helper、查询与路由，保留 fixture-v1 历史并写入新检查点 |

用例 1 中场景组保存了独立条件、根因、两个实例、两个反驳项和报告映射；基线组用一个漏洞节点和若干证据／排除节点表达同样的安全判断。额外拆分提供了不同查询粒度，但本轮没有证明它提高判断质量，不能把节点更多当作收益。

这组简单输入没有区分出安全判断准确率的优势。结论仅为：本场景包能完成这些工作，且没有引入已观察到的核心误判；不能据此声称优于通用 Skill、提高真实漏洞召回率或降低误报率。

两组最初都出现把写入参数附给读命令的错误，随后恢复：`capabilities` 拒绝 `--agent`，`context` 拒绝 `--no-init`。任务公共提示同时强调这些写入参数，存在诱导因素；因此不把这部分计作组间差异。已在 [CLI 约定](../references/pinwhy.md) 明确参数按命令区分，正式示例的对应读取形式由协调者实际运行通过。

## 命令与包验证

- 开发 CLI：合成示例成功导入 **11 个节点、20 条关系、1 次编辑**。`batch --check` 未创建节点；同请求重试不重复；receipt 为 committed；冲突 request-id 被拒绝且未增加节点。
- 反证与未知：读回 shell 候选为 refuted、未知条件为 blocked，均无严重度；报告映射的两个 groups 目标是实际 finding ID。
- 查询与恢复：限定明细时 `total=3`、返回 1 条且 truncated=true；1000 预算的 context 显式报告省略，仍保持非指令策略；导入前检查点的历史读取为 0 节点。
- 导出：按本次标签、finding 类型和 confirmed 状态导出 Markdown／SARIF；SARIF 产生 2 条实际有位置的结果。没有请求不存在的 JSON 导出。
- 稳定安装 CLI：同为 0.10.1，未声明 asOf；按其能力导入同一示例、重试、读取回执和恢复成功，没有升级或修改安装副本。开发 CLI 声明 asOf，并单独完成历史读取验证。
- 仓库相关检查：`node --test test/skill.test.js test/methods.test.js test/docs.test.js test/packaging.test.js`，28 项通过。它们检查通用包与契约，不能单独证明新场景有效；本轮另检验了新场景的元数据、本地链接、自包含引用、公开内容与完整打包列表。

这些是正常调用与重试的冒烟证据，没有注入进程中断／掉电故障；不声称新测了内核的故障恢复能力。

## 独立审阅与修订

独立审阅指出运行验证门槛缺少宿主文件与 IPC 的可见性限制。入口已补充 OS 强制最小可见范围、排除宿主主目录／凭据／代理与守护进程套接字／保留输出／其他参与者目录、禁止继承开放句柄，以及不安全时继续静态研究。证据保留补充进程退出、受信目录句柄、不跟随链接、拒绝不安全条目与限长读取。原审阅者只读复核后确认该问题关闭。

行为场景运行使用修订前的初稿；随后修订仅涉及该运行安全门槛、CLI 参数说明和评估的表示等价性说明。六次任务均未执行目标源码，因此本轮没有运行验证所需隔离环境的实测证据；文档审阅也不替代 OS 隔离验证。
