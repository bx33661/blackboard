# 可复现的性能基线

性能测量只创建临时的合成黑板，不读取当前目录、真实项目黑板、宿主会话或已安装的 release。成功和失败都会清理临时目录；只有显式指定的 JSON 报告留在磁盘。

## 运行

```sh
# 日常 / CI：1,000 节点、10,000 事件，每项 3 次
node scripts/benchmark.mjs --quick --output /tmp/blackboard-quick.json

# 完整：分别测 1,000 和 10,000 节点，各 100,000 事件，每项 5 次
node scripts/benchmark.mjs --full --output /tmp/blackboard-full.json

# 同一测量脚本，对比另一个源码目录；不要求对方包含此脚本
node scripts/benchmark.mjs --full --source /absolute/path/to/baseline --output /tmp/blackboard-baseline.json

# 缩小数据验证工具本身 / 排除并发争用
node scripts/benchmark.mjs --nodes 100 --events 1000 --runs 2 --no-concurrency
```

JSON 含机器、Node 版本、时间、源码内容指纹、固定输入 SHA-256、每项原始样本、nearest-rank p50/p95、RSS 采样和完整性结果。源码指纹覆盖 package.json、可用的 package-lock.json 及完整 bin/、lib/ 文件树，包含拆出的存储、语义与回执实现；测量脚本另记 SHA-256。`changedDuringRun: true` 的报告不宜作版本比较，也不能通过显式预算检查。

## 可选本地预算

默认仍只收集观测；显式提供 `--budget <JSON>` 时才检查延迟限制。每条规则指定数据规模、指标、p50/p95 和毫秒上限，必须与本次实际测量匹配；缺少样本、未知指标或无效阈值报错，不能当作通过。以下是固定机器上可调整的示例，不是跨平台性能承诺：

```json
{
  "schema": "blackboard.performance-budget.v1",
  "limits": [
    { "nodes": 1000, "events": 10000, "metric": "fullReplay", "statistic": "p95", "maxMs": 100 },
    { "nodes": 1000, "events": 10000, "metric": "write", "statistic": "p95", "maxMs": 250 }
  ]
}
```

```sh
node scripts/benchmark.mjs --quick --budget /tmp/blackboard-budget.json --output /tmp/blackboard-budget-report.json
```

报告增加 `budget.passed` 和逐项 `checks`，保留实际耗时。超限时依旧输出并保存完整报告，进程非零退出。CI 的共享机器继续只收集基线，不默认应用本地预算。


## 指标定义与限制

| 指标 | 实际测量范围 |
| --- | --- |
| `processColdReplay` | 新 Node 进程启动、模块加载、完整回放及校验指纹输出；**不清空操作系统文件缓存**，不是冷磁盘测试 |
| `fullReplay` | 在当前进程中读取全部 events.jsonl、解析并建立投影；指纹和断言不计入计时 |
| `contextProjection` | 从已经回放的图构造 4,000-token / 24-item 预算上下文，不含读取日志 |
| `recoveryContext` | 完整回放加相同预算的上下文构造 |
| `write` | 在独立克隆的事件日志上调用一次 addNode，包含写锁、兼容检查、回放、追加和状态缓存；不含克隆与断言 |
| `concurrency.write` | 两个子进程各写 2 次（full 为 3 次），包含锁竞争 |
| `concurrency.concurrentRead` | 写进程运行时，父进程反复完整回放的耗时；样本数随运行情况变化 |
| `rssBytes` | 各阶段父/子进程 `process.memoryUsage().rss` 的观测值及最大值；不是 OS 峰值，也不是进程内存总和 |

重复次数很少，p95 在 3/5 个样本时就是最大值。CI 共享机器和并行任务会产生噪声；默认不设硬延迟阈值，也不据一次运行声称加速或退化。本地预算只适用于调用方指定的环境和数据规模。测量进程保留多个阶段的对象，RSS 用于观察总体压力，不能直接归因于单个操作。

## 完整性门槛

测量中的以下情况均使命令非零退出，而不是生成一个看似成功的报告：

- fresh-process 与同进程完整回放投影不一致；
- 读取前后事件文件 SHA-256 不一致；
- 写入改写了原日志前缀，或一次单节点创建不只增加一条事件；
- 并发写丢失、重复、事件 ID 重复、节点数量不符；
- 回放产生坏行、未来版本、拒绝事件或未知操作。

合成数据包含已反驳节点、显式置信度、未知节点类型、关系、游标、交接点和反复 patch。它用于测事件回放与恢复成本，**不代表浏览器布局、真实 Agent 的恢复质量或模型调用延迟**。这些需要独立评测。

## 首轮本地实测（2026-10-22）

环境：macOS arm64、Apple M4、10 逻辑核、24 GiB、Node v26.11.1。基线和迭代副本使用相同测量脚本、相同 fixture SHA-256；每项 5 次。执行时机器上存在其他迭代任务，数据只作后续复测的起点。

单位：ms，表内为 p50 / p95。

| 源码 | 节点 / 事件 | 完整回放 | 恢复上下文 | 单次写入 |
| --- | --- | --- | --- | --- |
| 迭代前 | 1k / 100k | 54.22 / 56.60 | 53.54 / 64.52 | 96.80 / 101.74 |
| 迭代前 | 10k / 100k | 63.03 / 65.04 | 68.32 / 84.05 | 108.13 / 113.87 |
| 迭代中副本 | 1k / 100k | 52.35 / 56.52 | 55.55 / 64.27 | 146.73 / 158.10 |
| 迭代中副本 | 10k / 100k | 58.15 / 58.79 | 67.77 / 70.22 | 170.04 / 174.78 |

四组的只读原文、回放一致性、写入前缀及并发写入校验均通过。以上“迭代中副本”不是最终发布性能承诺；交付前或写入路径修改后应重新运行 full。写入尾延迟值得复测和剖析，不能仅据这张表推断原因。

## 优化顺序

1. 在空闲且固定的机器上保存基线/修改版 JSON，先检查输入指纹和源码稳定性，再比较样本分布。
2. 若完整日志读取成为瓶颈，再评估可丢弃的字节偏移缓存/索引；缓存丢失或损坏时必须回退到全量事件回放，并验证结果完全一致。
3. 浏览器单独测首屏、交互、布局和流更新后，才决定是否需要 SSE 增量传输。
4. 本轮不引入数据库，不裁剪事实日志，也不预设索引或增量广播能改善真实负载。

## 读取复用后的同机验证

本轮修改前后均使用 Apple M4 / macOS arm64 / Node v22.23.1，每项 5 次；两种规模的 fixture SHA-256 均相同。修改版的源码起止指纹一致，读取原文、回放一致性、写入前缀与并发写入精确性检查全部通过。计时范围保持一致，未清空系统页缓存。

单位 ms，表内为 p50 / p95：

| 节点 / 事件 | 源码 | 完整回放 | 恢复上下文 | 单次写入 |
| --- | --- | --- | --- | --- |
| 1k / 100k | 修改前 | 67.3 / 85.4 | 68.3 / 69.7 | 136.1 / 137.6 |
| 1k / 100k | 读取复用后 | 80.5 / 87.0 | 67.0 / 68.3 | 77.6 / 77.8 |
| 10k / 100k | 修改前 | 80.7 / 126.4 | 88.7 / 144.0 | 156.2 / 200.3 |
| 10k / 100k | 读取复用后 | 71.8 / 94.3 | 83.4 / 86.3 | 84.5 / 121.8 |

单次写入现在复用锁内已读取的日志供回执和工作图使用；CLI / HTTP 增量上下文也复用一份事件快照，隔离节点对象以保留历史原值。多 Agent Digest 共用统计、节点排序和身份分组。单次写入的本机样本改善明显；回放的两种规模结果方向不同，不能概括为全路径加速。

本地预算显式取修改前相同规模的 `fullReplay`、`recoveryContext`、`write` 的 p95 × 1.5，六条限制均通过；并发竞争尾延迟不在这些规则中。完整样本、机器、输入指纹、预算逐项结果保存在调用方指定的 JSON 中，CI 继续只观测。上述数据是本机小样本验证，不是跨机器延迟承诺。
